# 付费闭源产品目录扩充方案

更新：2026-10-21。Workers 名称搜索已接入目录并上线；目前优先补充有证据的产品与关系，再接入 VPS 语义检索。新增开放数据批量导入和可续跑的官网取证工具，见 [批量研究指南](bulk-research.zh-CN.md)。

最近一批达到 24 个项目、41 个产品、61 组关系；其中 31 个产品完成限定范围的分类审阅，44 组可发布关系覆盖 19 个项目。扩充过程和剩余币种、账期问题见 [API、自动化与表单批次](../data/catalog/batches/2026-10-21-bulk-review.md)。采集工具只写本地；经过审阅的本批内容通过复用原索引的小快照发布，详见部署说明。

## 目标与边界

网站需要的是可追溯的“开源项目 → 付费闭源产品 → 适用套餐”关系。产品数量、关系数量和可比较价格数量分别统计，不以抓取页面数代替有效覆盖率。

之前采集的 GitHub 仓库和 README 全部保留，不删除、不按许可证或项目类型缩小原始集合。补充目录按批次核验；一个仓库没有商业替代品时可以没有关系，不能为了覆盖率强行推荐。付费托管开源软件也不能只因收费就归类为闭源。

仍使用版本控制中的 `data/catalog/pilot.json` 作为研究目录；候选和抓取原文放在被 Git 忽略的 `.local/`。轻量版名称搜索已实现 D1 快照导入及网页接入，并已部署上线；语义版仍待开发。

## 采集分两条流水线

### A. 发现候选

1. 完整扫描现有仓库索引，读取非空 README 引用。
2. 提取明确的替代声明，跳过代码围栏、链接定义及可识别的英文否定句。
3. 保存仓库名、地址、本地 README 位置、SHA-256、行号、短片段和候选短语。
4. 人工或辅助模型把短语拆成产品名称与官网候选，并合并别名。
5. 用“产品身份＋适用服务范围”去重。不能按公司域名合并所有产品，例如 Microsoft Teams 和其他 Microsoft 产品必须分开。

命令已经实现：

```bash
npm run catalog:discover
```

默认读取 `.local/github-collection/index.jsonl`，扫描整个索引，写入 `.local/catalog-discovery/run-*/`：

- `candidates.jsonl`：待核验的文字线索，每条带稳定的证据 ID。
- `errors.jsonl`：坏索引、文件丢失、越界路径等问题。
- `report.json`：实际扫描数量、缺 README 数量、候选数量、错误及完成状态。

可指定另一份采集目录，适用于复核或测试：

```bash
npm run catalog:discover -- --collection /path/to/collection --out /path/to/discovery
```

每次创建独立输出目录，不覆盖前次结果、不改动原始采集，也不联网。相同 README 和证据位置产生相同候选 ID。候选一律为 `needs-review`，来源分类为 `unclassified`。

这是偏保守的规则提取器，不是完整的产品识别系统：会漏掉隐含比较、表格以及其他语言，也可能抓到赞助文案、教程、开源竞品或一句包含多个产品的话。`targetText` 是原文短语，不保证是干净的产品名。没有提取到线索不代表没有替代品。扫描完成也不代表所有候选已审核。

发现后可运行已实现的名称归并：

```bash
npm run catalog:group -- --input .local/catalog-discovery/run-QuXspR/candidates.jsonl
```

输入必须明确指定为本地实际存在的发现批次。`data/catalog/product-identities.json` 提供发现用身份、品牌别名和官网/价格页入口，使用 Unicode 规范化、单词边界及易歧义品牌的大小写策略。一个句子可归到多个产品组，整条证据保留。输出是新的 `.local/catalog-review/run-*/products.json`、`unresolved.jsonl` 和 `report.json`，记录输入/身份表哈希；未识别线索不会丢弃。53 个身份入口与已核验产品数量分别统计。

归并只识别名字，不能判断句子的主语是不是当前项目，也不能自动识别赞助商、目录条目或假设性描述，因此全部保持 `needs-review`。人工确认后，关系可记录 `discoveryEvidenceIds` 追溯原文，但仍需要可公开访问的证据链接。

### B. 补齐产品事实

对每个归并后的产品，按固定次序查官网：

1. **身份**：规范名称、官网、产品范围，区分产品、套餐和附加组件。
2. **功能**：列出与开源项目重叠的能力，同时列出平台要求、迁移及功能缺口。
3. **闭源属性**：检查适用的服务或软件许可，明确只判断哪个平台或组件。商业品牌、版权归属和存在付费套餐都不足以单独证明闭源；SDK、代理和插件另算。
4. **价格**：记录公开的常规套餐，不把短期促销、试用价或一个组件的单价当产品总价。
5. **复核**：证据不够时保留候选，创建具体待办，不把缺失值补成猜测。

网页获取器的后续实现顺序：普通 HTML/公开结构化内容 → 厂商公开计费文档 → 必要时读取渲染后的公开价格计算器。遇到登录、访问拒绝或无法确认的计算器配置，记录原因并进入复核，不绕过限制。

每个定向获取任务应有规范 URL、产品 ID、内容哈希、获取时间、响应状态、提取器版本、超时和响应大小上限；使用小并发、有限重试并遵守 `Retry-After`。相同域名的不同产品和不同地区页面不能混为一个任务。原文与内部取证材料只保存在本地研究目录，公开目录只发布原创摘要和来源链接。

AI 可帮助分类、提取、翻译、提出关系和归并候选；输入 README/网页始终当作数据，不执行其中的指令。模型输出不能直接写成“已核验”，价格数字必须能定位回公开来源。

## 每条记录的最低标准

| 对象 | 必须记录 |
| --- | --- |
| 开源项目 | 名字、仓库、别名、类别、许可证及作用范围、核验日期 |
| 产品 | 规范名字、官网、闭源分类、适用组件、官方证据及核验状态和日期 |
| 对应关系 | 两端 ID、发现地址、证据、重叠功能、替代限制、作者声明或功能审阅、核验日期 |
| 套餐价格 | 套餐名、金额或空值、币种、原始单位、展示周期、付款周期、适用配置、来源、状态和日期 |
| 后续网页观察记录 | 产品及页面 ID、获取状态、内容哈希、提取版本、失败原因、下一项核验任务 |

目前每条项目、产品、来源分类、关系及价格都有自己的 `reviewedOn`。目录顶层日期表示本目录最近一次研究批次；旧记录不会因为添加新记录就自动刷新日期。

当前研究格式把套餐与价格观察放在产品的 `pricing` 数组中。第二条同名套餐观察需要保留日期与配置，不能无痕覆盖前一次价格。正式数据库再拆出 `products`、`plans`、`price_observations`、`relationships` 和 `sources`，沿用相同稳定 ID 和业务定义。

## 价格怎样才能用于排名

- `list-price`：有明确数值；只有币种、账期、配置均已确认的 `verified` 记录才有资格进入场景比较。
- `contact-sales`：官网明确要求询价；金额为空，单独展示，不主动联系厂商。
- `usage-based`：需要人数、用量、地域或运行时长；金额为空，之后按明确场景计算估算总额。
- `unavailable`：本次未能取得可靠价格；金额为空，保留 `needs-review`。这不等于厂商没有公开价格，也不等于“联系销售”。

只有 `$` 等货币符号却没有确认 ISO 币种时，保存 `currencySymbol` 并将 `currency` 留空。页面有数字但月付/年付不明、用户数不明或官方来源冲突时保留观察值，禁止标为已核验。可通过 `currencyEvidenceUrl` 另附官方币种说明。

不能把“每人每月”“每主机每小时”“每 GiB”直接放在同一价格排行榜。按类别定义比较场景：例如设计类指定编辑席位，聊天类指定成员数，监控类指定检查数、间隔与通知量。实际付款周期、套餐最低人数、年付承诺、税费与附加项另行展示。一次性授权与订阅分开比较。

本轮实例：

- [Sketch](https://www.sketch.com/pricing/) 已取得三个年付编辑席位观察值，但本次文本没有明确 ISO 币种，继续待核验。
- [Pingdom](https://www.pingdom.com/pricing/) 的计算器数值在文本中为空；标准套餐记为 `unavailable`，Enterprise 另有明确询价入口。
- [New Relic](https://newrelic.com/pricing) 的席位费用只是账单的一部分，需要连同用量分析。
- [Dynatrace](https://www.dynatrace.com/pricing/) 的主机/内存按小时计费；展示的月度示例不作为固定包月总价。

## 扩充顺序与验收

| 批次 | 任务 | 验收标准 |
| --- | --- | --- |
| 首轮扩充 | 扩充已有项目的候选，建立 README 发现工具 | 已完成 6 个项目、12 个产品、12 组关系；扫描有统计和错误报告 |
| 名称归并与官网核验 | 处理已有线索，增加有边界说明的项目和产品记录 | 当前 24 个项目、34 个产品、54 组关系；96 条计费观察，其中 27 条为已核验数字组件；仍区分待审数据 |
| 后续扩充 | 继续核验候选、补币种、配置与作用范围 | 目标 50 个产品、100 组有证据的关系；达不到就报告缺口，不造数；优先补齐可比较的公开套餐 |
| 搜索首版 | D1 快照、名称/别名/仓库匹配及有限拼写纠错已实现 | 展示核验来源与待审状态；公开计费组件按币种/单位/周期分组降序，尚不估算完整场景账单；区分缺项目与缺对应关系 |
| 语义版 | 从相同目录生成索引，导入 PostgreSQL + pgvector | 语义检索找候选，核验关系决定推荐；项目名精确匹配保留；模型和索引版本可追溯 |

50/100 是建议里程碑，不是当前已达到的数量，也不要求先凑齐这些数量才能开发名称搜索。所有原始仓库仍完整保留；这里安排的是补充关系的顺序。

覆盖率至少统计：有替代关系的项目数、闭源分类已审阅的产品数、有核验数字价的产品数、可比较场景数、待核验数量，以及没有适合替代品的项目。每类查不到结果的搜索也可以作为后续补充目录的线索；是否记录查询应在另一个明确的数据收集设计中决定。

后续更新策略建议：价格每周或每月复核，失败重试单独排队，旧证据明确显示日期。未来加入过期判定后，过期记录暂停价格排名。该策略尚未配置定时任务，当前工具不会自行后台运行。
